# Moment 后续优化路线

> 记录日期：2026-09-04  
> 当前状态：待评估，尚未创建对应 OpenSpec change，尚未进入实现  
> 适用范围：Bean Blog 的 `/moment` 信息流  
> 用途：记录当前实现中值得继续优化的问题、触发条件和建议拆分。本文不是使用手册，也不表示所有事项都必须实施。

## 当前结论

现有 Moment 已具备短 Markdown 正文、图片画廊、地点、标签、置顶、草稿、相对时间、随机封面和滚动分批展示，桌面端与移动端的主要浏览流程已经可用。下一阶段不宜继续做无目标的视觉调整，应优先处理媒体加载、返回状态恢复和随机封面可靠性，再根据真实内容规模补充分组导航与作者工具。

以下事项应分别建立小范围 OpenSpec change，不继续扩大已经完成的 `add-moment-feed`。

## P1：媒体加载与布局稳定性

### 响应式图片

当前 Moment 缩略图直接加载原图。图片较多或原图较大时，会增加首屏流量和解码开销；单图若没有稳定的宽高信息，还可能在加载过程中造成布局偏移。

- [ ] 在构建期为本地图片生成缩略图和 WebP、AVIF 等适合浏览器的格式。
- [ ] 为图片输出 `srcset` 与合理的 `sizes`，按显示尺寸选择资源。
- [ ] 为单图和画廊项提供稳定的尺寸或宽高比，降低累计布局偏移。
- [ ] 图片预览继续允许查看原图，不以缩略图替代完整资源。
- [ ] 远程图片无法在构建期可靠处理时，保留原地址作为回退，不阻止 Moment 构建。
- [ ] 明确生成资源的缓存、清理和重复图片复用策略，避免构建产物无限增长。

实施前应先用真实图片测量构建时间、产物体积、首屏传输量和布局偏移，避免仅凭源文件大小决定转换策略。

### 随机封面加载

当前随机封面支持配置本地或远程图片，但服务端渲染先输出第一张，客户端挂载后再选择随机项，可能产生首屏闪切或重复下载。远程封面加载失败时也缺少自动尝试下一张的策略。

- [ ] 在不破坏服务端渲染稳定性的前提下确定随机选择时机。
- [ ] 预加载选中的封面，加载完成后再平滑替换当前画面。
- [ ] 当前候选加载失败时尝试下一张，全部失败时保留稳定的默认封面或背景。
- [ ] 避免同一次访问重复选择，并评估返回页面时是否沿用原封面。
- [ ] 为远程地址补充失败、超时和格式不受支持的浏览器验收。

## P1：信息流状态恢复

当前滚动加载本质上是逐步挂载已经下载到浏览器的 Moment 数据。用户打开较靠后的动态或离开页面后返回时，已展示数量和滚动位置可能重置，导致需要重复滚动。

- [ ] 保存当前已展示批次或 `visibleCount`。
- [ ] 保存离开 `/moment` 前的滚动位置或最后可见 Moment。
- [ ] 返回页面时先恢复足够的 DOM，再恢复滚动位置，避免定位到尚未挂载的内容。
- [ ] 区分站内返回、直接访问和刷新，避免所有入口都强制恢复旧位置。
- [ ] 对内容数量变化、置顶项变化和目标 Moment 被删除的情况提供合理回退。
- [ ] 验证浏览器前进、后退、fragment 深链和移动端页面缓存行为。

可以优先评估 History API 与 `sessionStorage`，不需要为这项能力引入持久化服务。

## P2：长信息流导航

### 年月分隔

当 Moment 数量持续增加后，单一连续列表会缺乏时间方向感。建议增加轻量的年月分隔，但继续保持当前滚动浏览方式，不改回分页。

- [ ] 由构建期 Moment 模型提供稳定的年月分组信息。
- [ ] 分隔标题保持紧凑，不把每个月包装为独立卡片。
- [ ] 置顶内容与普通时间分组的关系需要明确，避免时间顺序产生歧义。
- [ ] 加载新批次时正确插入分隔，不重复显示同一个月份。
- [ ] 为辅助技术提供清晰的标题层级。

### 深链反馈

单条 Moment 已有稳定 fragment，可以通过分享链接定位，但目标卡片缺少明确的视觉反馈，尤其在信息流较长时不易确认定位结果。

- [ ] 使用现有语义颜色为目标 Moment 增加短暂强调。
- [ ] 尊重 `prefers-reduced-motion`，不依赖闪烁或大幅动画。
- [ ] 焦点与滚动定位不应被固定头部遮挡。
- [ ] 强调结束后恢复普通状态，不长期改变卡片视觉层级。

### 相对时间刷新

当前相对时间主要在组件挂载时计算。页面长时间保持打开或跨越午夜后，“刚刚”“昨天”等文本可能过期。

- [ ] 页面重新获得可见性时刷新相对时间。
- [ ] 仅在需要时使用低频定时刷新，避免每条 Moment 各自建立计时器。
- [ ] 继续保留标准 `datetime` 和完整时间提示。

## P2：作者工作流

随着 Moment 数量增加，手工创建目录、文件名、日期和正文模板容易产生格式错误。可以增加一个轻量命令，例如 `pnpm moment:new`。

- [ ] 自动生成当前时间、稳定 slug 和短正文模板。
- [ ] 支持可选的地点、标签、置顶和图片字段，不把非必填项全部写入模板。
- [ ] 检查 slug 冲突、日期格式和目标路径。
- [ ] 可选复制、压缩或重命名本地图片，并提示填写有意义的替代文本。
- [ ] 生成结果继续使用现有 `src/moments/**/*.md` 数据源，不建立第二套内容模型。
- [ ] 写作校验复用现有解析与校验函数，避免 CLI 与构建期规则漂移。

该命令属于作者工具，不应改变普通 Markdown 可直接手写的能力。

## 技术债与小问题

### 文档语义与数据消费

- [ ] `MomentCard.vue` 当前每条动态都以作者名作为 `h2`，页面大纲会出现大量重复标题。应为每条动态提供更合适的语义标题，同时保持朋友圈式视觉不变。
- [ ] `title` 与 `updated` 已进入 Moment 数据模型，但页面未充分消费。需要决定正式用途，或移除没有明确语义的字段。
- [ ] 使用手册应明确随机封面既支持 `src/public` 中的本地资源，也支持远程 URL，并说明远程资源的可用性和隐私取决于第三方服务。
- [ ] 旧 frontmatter `images` 当前仅用于迁移兼容，应记录弃用策略和移除节点，避免长期维护两套写法。

### 构建期实现

`moments.data.ts` 会再次解析 Markdown，并通过环境数据向 Markdown 渲染阶段传递图片元数据。这是当前 VitePress content loader 能力限制下的折中方案，不应在没有替代能力时贸然重写。

- [ ] 升级 VitePress 时回归 Moment 正文解析、图片元数据传递和热更新行为。
- [ ] 若 VitePress 后续提供更直接的 token 或 loader 元数据通道，再评估收敛重复解析。
- [ ] 保持 Markdown 扩展基于 parser token，不改为整篇 Markdown 字符串替换。

### 数据传输规模

当前“滚动加载”只减少初始挂载到 DOM 的卡片数量，所有 Moment 数据仍会在首次进入页面时下载。这对当前规模足够简单可靠，不需要立即引入接口或运行时服务。

- [ ] 当公开 Moment 接近 200 条，或首屏加载的数据包接近 200 KB 时重新测量。
- [ ] 若达到阈值并出现可感知问题，优先考虑按年月生成静态 JSON 分块。
- [ ] 分块后仍保持静态部署、构建期内容模型和连续滚动体验。
- [ ] 搜索、Feed、sitemap 等消费者继续复用统一内容模型，不单独抓取分块文件作为新数据源。

上述数量和体积是重新评估的触发点，不是必须分块的硬性上线条件；最终决定应以真实网络和浏览器性能为准。

## 可选能力

以下能力有价值，但不应优先于媒体、状态恢复和可靠性问题：

- [ ] 在支持 Web Share API 的移动端提供系统分享，桌面端和不支持的浏览器继续复制链接。
- [ ] 为 Moment 提供独立 Feed，并明确正文、图片和单条链接的输出形式。
- [ ] 若需要单条 Moment 的 Open Graph 预览，增加静态详情路由；URL fragment 不会发送给服务器，无法为每条动态生成独立服务端元数据。
- [ ] GitHub 回复系统保持独立 change，并先完成技术验证，不与本路线中的体验优化捆绑实施。

GitHub 回复系统的完整身份、数据、安全和部署方案见 `docs/moment-github-reply-system.md`。

## 建议的 OpenSpec 拆分

### `optimize-moment-media`

- 响应式图片与缩略图。
- 单图和画廊布局稳定性。
- 随机封面预加载与切换。
- 本地和远程资源失败回退。

### `improve-moment-navigation`

- 返回页面时恢复展示状态和滚动位置。
- 年月分隔。
- fragment 目标强调。
- 相对时间刷新。

### `add-moment-authoring-cli`

- 新建 Moment 模板。
- 可选图片处理。
- slug、日期、字段和替代文本校验。

### `add-github-moment-replies`

- 按 `docs/moment-github-reply-system.md` 独立推进。
- 阶段 0 先验证 GitHub App、Discussion、Worker 和访客身份发表链路。

每个 change 只包含自身目标。媒体优化不应顺带重构信息流，导航优化不应引入评论服务，作者 CLI 也不应建立独立于构建期文章模型的数据规则。

## 推荐顺序

1. 测量当前 Moment 图片体积、布局偏移和随机封面的真实加载行为。
2. 实施 `optimize-moment-media`，先解决访问成本和封面失败回退。
3. 实施 `improve-moment-navigation`，改善长信息流返回、定位和时间感知。
4. 根据实际发布频率决定是否实施 `add-moment-authoring-cli`。
5. 当内容规模达到重新评估阈值时，再决定是否采用静态 JSON 分块。
6. GitHub 回复系统按独立路线完成技术验证后再决定是否上线。

## 后续验收关注点

未来实施上述任一 change 时，至少应回归：

- 桌面端与移动端的连续滚动、返回恢复和 fragment 定位。
- 本地图片、远程图片、单图、九宫格和图片预览。
- 本地封面、远程封面、失败回退和随机选择稳定性。
- 明暗模式、减少动态效果设置和键盘操作。
- 草稿过滤、置顶排序、日期解析和热更新。
- 生产构建后的静态路由、资源地址与部署 base。
- 使用手册、单元测试和 Playwright 场景与最终行为一致。
